# ADR-0001：采用单仓库 Monorepo

## 状态

已接受，初始仓库阶段。

## 背景

项目同时包含甲方原型、微信小程序、业务 API、管理员 Web、智能体运行时、共享契约、数据种子、部署和验收材料。各模块需要独立部署与测试，但必须共享版本化契约和同一交付节奏。

## 决策

采用一个 Git 仓库统一管理所有模块，默认分支为 main。

JavaScript/TypeScript 项目使用 pnpm workspace 管理依赖和根级递归命令。智能体服务如果采用 Python 或其他运行时，可维护独立的依赖与锁文件，不强制转换为 Node 项目。

暂不引入 Turborepo、Nx 或其他任务编排器。等真实应用初始化、构建耗时和缓存需求明确后，再通过新的 ADR 决定是否增加。

## 边界

- miniapp-frontend 只能调用业务 API。
- miniapp-business-backend 是业务数据事实源。
- agent-server-backend 通过私有契约提供结构化候选结果。
- contracts 是跨工程接口的唯一事实源。
- 每个可部署应用独立拥有依赖、测试、构建、镜像和发布版本。
- 禁止应用通过跨目录相对导入绕过服务边界。

## 结果

优点：

- 一个提交可以原子化更新契约和多个消费者。
- 原型、实现、测试、部署与验收记录能够保持同一版本。
- 根级命令可统一执行质量检查。
- 便于共享 CI 规范和安全策略。

代价：

- 必须控制工作区依赖方向，避免无边界共享。
- CI 需要按受影响模块执行，避免所有服务无差别重建。
- 多语言工具链需要分别维护锁文件和缓存。
